# Как сделать отчёт по проекту с тестами

Ниже — практичный шаблон отчёта, который можно использовать для лабораторной/курсовой.

## 1) Цель и постановка задачи
Опишите:
- цель: измерить QoS (RTT, потери) в разных условиях;
- что сравнивается: например, baseline vs. перегруженный канал;
- критерии: средняя задержка, p95, потери, стабильность.

## 2) Окружение эксперимента
Зафиксируйте в отчёте:
- ОС, версия Python, зависимости;
- цель измерения (`--target`), длительность (`--duration`), интервал (`--interval`);
- если Mininet: топология и параметры линков (delay/loss/bw).

Пример команды:
```bash
python src/main.py --target 8.8.8.8 --duration 120 --interval 1
```

## 3) Методика
Рекомендуемая методика:
1. Провести минимум 3 прогона на одинаковых параметрах (для устойчивости вывода).
2. Отдельно провести прогоны в изменённых условиях (например, искусственная потеря пакетов).
3. Сохранить все артефакты (`results/raw/*.csv`, `results/plots/*.png`).

## 4) Что вставлять в отчёт
### 4.1 Таблица сводных метрик
Из `results/raw/ping_stats.csv` вставьте колонки:
- `run_id`, `target`, `duration_sec`, `interval_sec`;
- `packet_loss_percent`;
- `latency_mean`, `latency_median`, `latency_p95`, `latency_min`, `latency_max`, `latency_std`.

### 4.2 Графики
Вставьте `latency_histogram_<run_id>.png` для каждого ключевого сценария.

### 4.3 Краткий вывод
Для каждого сценария ответьте:
- как изменился средний RTT;
- насколько вырос p95 (хвост задержек);
- увеличились ли потери и насколько.

## 5) Раздел «Тесты» в отчёте
В отчёте лучше разделить тесты на 2 уровня.

### 5.1 Unit-тесты (логика кода)
В проекте есть автотесты `tests/test_ping_probe.py`, проверяющие парсинг RTT для Linux/Windows/RU выводов ping и обработку случаев без RTT.

Запуск:
```bash
python -m unittest discover -s tests -v
```

В отчёт добавьте:
- команду запуска;
- итог (`OK`, число тестов);
- скрин/лог консоли.

### 5.2 Функциональные тесты (end-to-end)
Проверьте, что после запуска измерения создаются нужные артефакты:
- `results/raw/ping_results_<run_id>.csv`;
- `results/raw/ping_stats.csv`;
- `results/plots/latency_histogram_<run_id>.png`.

Чек-лист для отчёта:
- [ ] команда запуска выполнена без ошибок;
- [ ] CSV с сырыми результатами создан;
- [ ] сводная статистика добавлена;
- [ ] PNG-гистограмма создана.

## 6) Рекомендуемая структура итогового отчёта
1. Титульная часть
2. Цель и задачи
3. Описание инструмента и архитектуры
4. Методика эксперимента
5. Результаты (таблицы + графики)
6. Тестирование (unit + функциональные)
7. Выводы
8. Приложение (сырые логи/команды)

## 7) Критерии хорошего отчёта
- Воспроизводимость: по отчёту можно повторить эксперимент.
- Прозрачность: есть исходные CSV и команды.
- Корректность: выводы опираются на метрики, а не на «визуальное впечатление».
- Полнота: есть как минимум базовый и стресс-сценарий.
